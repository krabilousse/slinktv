# Android TV Twitch feasibility research

Checked 2026-11-08 against upstream documentation, source, and package indexes. This is source research, not a successful Android build or playback test. Recommendations below are engineering judgments; runtime gates remain open.

Implementation follow-up: the delivered prototype uses Java, Python 3.11 (to retain ARM 32-bit firmware support), Chaquopy 17.2, Streamlink 8.6.3, and Media3 1.9.3 with the resolver-only path. APK packaging and host Linkus7 network checks succeeded. Native 16 KB support and Android runtime playback remain open; see [verification](verification.md). Suggestions below describe the researched options, not a claim that every gate has passed.

## Decision

**Phase 1 is plausible, with two separate gates: Android Python packaging and Twitch stream acquisition.** Start with Kotlin, embedded Media3, and Streamlink's Python API through Chaquopy. No external player, Termux, desktop process, or remote resolver should be required for the normal path. Streamlink exposes stream objects independently of its CLI; Media3 accepts HLS playlists. [Streamlink API](https://streamlink.github.io/api_guide/quickstart.html), [Media3 HLS](https://developer.android.com/media/media3/exoplayer/hls).

**Phase 2 phone/QR account login is officially supported without a backend.** However, account API authorization and authenticated video playback are different capabilities. Do not promise that QR login enables subscriber-only playback, Turbo benefits, or every quality tier. [Twitch device flow](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/#device-code-grant-flow), [Streamlink authentication](https://streamlink.github.io/cli/plugins/twitch.html#authentication).

## Phase 1: packaging and playback

### Streamlink + Chaquopy

- Streamlink **8.6.3** requires Python **3.10+**. Its declared dependencies include `certifi`, `isodate`, `lxml >=5,<8`, `pycountry`, `pycryptodome >=3.4.3,<5`, `PySocks`, `requests`, `trio`, `trio-websocket`, `urllib3`, and `websocket-client`; Python 3.10 also needs compatibility packages. The main native-wheel checks are **lxml and pycryptodome**. Installing the full package still requires them even when using only Twitch. [Pinned package metadata](https://github.com/streamlink/streamlink/blob/8.6.3/pyproject.toml).
- Upstream installation documentation does not offer an official Android distribution. Embedding the library is a port/integration responsibility, not established upstream Android support. [Installation and packaging ownership](https://streamlink.github.io/install.html#package-availability).
- Chaquopy **17.2.0** supports Python 3.10–3.15, requires `minSdk >=24`, and documents AGP 7.3–9.5 compatibility. Python **3.12+ supports only `arm64-v8a` and `x86_64`**; 32-bit `armeabi-v7a`/`x86` needs Python 3.11 or earlier. Build-host Python must match the embedded major/minor version. Python and requirements are packaged at build time; apply Chaquopy in only one app/library module. [Gradle setup, Python and ABI support](https://chaquo.com/chaquopy/doc/current/android.html).
- **Suggested first packaging candidate:** Chaquopy 17.2.0, Python 3.13, Streamlink 8.6.3, `lxml==5.3.0`, `pycryptodome==3.21.0`, `arm64-v8a` plus `x86_64` for emulator development. Directly fetched Chaquopy indexes contain `cp313` Android API-24 wheels for both packages and both ABIs. These satisfy Streamlink's declared ranges; that is not proof of runtime compatibility. The web tool's cached indexes omitted these newer entries, so the live indexes were checked separately. [lxml wheels](https://chaquo.com/pypi-13.1/lxml/), [pycryptodome wheels](https://chaquo.com/pypi-13.1/pycryptodome/).
- Android 14+ means this project's minimum OS is API 34; choose `targetSdk` separately. Do not infer supported ABIs from OS version alone. For newer devices, verify **16 KB page compatibility of every native library**, including Python extensions and any LibVLC AAR. Chaquopy warns that old wheels can fail despite its runtime supporting 16 KB pages, and recommends Python 3.13+. [Chaquopy changelog](https://chaquo.com/chaquopy/doc/current/changelog.html), [Android native-library requirements](https://developer.android.com/guide/practices/page-sizes).
- Treat FFmpeg as a separate dependency if a selected stream needs muxing. Streamlink's `MuxedHLSStream`/FFmpeg path is distinct from plain HLS; embedding Python or LibVLC does not supply an executable FFmpeg to Streamlink. Keep the first test to a muxed audio/video HLS rendition. [HLS implementation](https://github.com/streamlink/streamlink/blob/8.6.3/src/streamlink/stream/hls/hls.py), [stream types](https://streamlink.github.io/api/stream.html).

### Choose the data path explicitly

**Resolver-only path:** call Streamlink off the UI thread, enumerate qualities, and pass a chosen HLS URL plus necessary request parameters to Media3. This is the smallest first playback test. A rendition URL is normally a fixed quality; automatic adaptation requires a multivariant playlist. Preserve required headers without forwarding account credentials indiscriminately to CDN hosts. Re-resolve on access failures rather than treating signed URLs as permanent. [Stream API](https://streamlink.github.io/api/stream.html), [Twitch acquisition code](https://github.com/streamlink/streamlink/blob/8.6.3/src/streamlink/plugins/twitch.py), [Media3 playlist behavior](https://developer.android.com/media/media3/exoplayer/hls).

**Streamlink-reading path:** `Stream.open()` provides file-like media bytes. A custom Media3 data source or an app-local loopback bridge could feed those bytes to the embedded player. This retains Streamlink's Twitch segment handling; merely forwarding its URL does **not** retain that handling. The bridge, cancellation, bounded buffering, timeouts, and progressive fragmented-MP4 recovery require implementation and testing. This is a proposal, not an upstream Android adapter. [Stream.open](https://streamlink.github.io/api/stream.html#streamlink.stream.stream.Stream.open), [Twitch reader/worker/writer](https://github.com/streamlink/streamlink/blob/8.6.3/src/streamlink/plugins/twitch.py).

**Prefer Media3 first.** It supports HLS MPEG-TS and fragmented MP4, with Android platform decoders determining available codecs. Start with H.264/AAC and enable HEVC/AV1 only after device capability checks. Media3 documents Apple low-latency HLS support but not community low-latency HLS; do not equate that with Twitch's `EXT-X-TWITCH-PREFETCH` implementation. [Media3 HLS support](https://developer.android.com/media/media3/exoplayer/hls), [decoder support](https://developer.android.com/media/media3/exoplayer/supported-formats#sample-formats), [Twitch prefetch parser](https://github.com/streamlink/streamlink/blob/8.6.3/src/streamlink/plugins/twitch.py).

**Embedded VLC is feasible via LibVLC**, distributed as `org.videolan.android:libvlc-all` AAR. It does not require the VLC app to be installed. Use it as a separately tested alternative if Media3 fails the selected byte-stream path. It adds native packaging and its own player lifecycle; it cannot repair Twitch authorization or integrity failures. VideoLAN distinguishes the LGPL LibVLC engine from the GPL Android application. [Official Android repository / LibVLC](https://github.com/videolan/vlc-android#libvlc).

### Playback limitations and browser fallback

- Streamlink's Twitch reader pauses output while filtering embedded ads; content resumes with a discontinuity. This is **not uninterrupted ad-free playback**. Its documentation notes VLC crash cases around discontinuities. Higher qualities can require account authentication and HEVC/AV1; fragmented MP4 can carry nonzero presentation timestamps. Test the exact selected player/path through ad transitions. [Twitch playback notes](https://streamlink.github.io/cli/plugins/twitch.html#embedded-ads).
- **Browser fallback can be necessary even for anonymous playback.** Twitch can demand a client-integrity token. Streamlink then launches Chromium and controls it through CDP; it is not simply opening a URL for the user. Android WebView is not a documented drop-in backend for this executable-based integration. An Android-specific implementation remains unproven; disabling the browser path can leave some streams inaccessible. [Integrity-token docs](https://streamlink.github.io/cli/plugins/twitch.html#client-integrity-token), [Chromium launcher](https://github.com/streamlink/streamlink/blob/8.6.3/src/streamlink/webbrowser/chromium.py), [CDP API](https://streamlink.github.io/api/webbrowser.html).
- Distinguish three credentials: the app's **OAuth user token**, the signed **playback access token** used to obtain HLS, and the **client-integrity token** sometimes required to acquire playback access. Device login does not replace all three. [Twitch plugin implementation](https://github.com/streamlink/streamlink/blob/8.6.3/src/streamlink/plugins/twitch.py).

## Phase 2: phone/QR login

1. Register **this app's own public client**. Twitch explicitly supports public device-flow clients without a client secret, including refresh. Public clients are restricted to device authorization and cannot use the other OAuth flows as an automatic fallback. Never embed a confidential secret or copy another application's client ID. [Device-flow client types](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/#device-code-grant-flow), [registration rules](https://dev.twitch.tv/docs/authentication/register-app/).
2. POST to `/oauth2/device` with `client_id` and `scopes`. Display the returned `user_code` and encode the returned `verification_uri` as a QR code. The phone opens Twitch, logs in, and approves; the TV polls `/oauth2/token` with `device_code` and `grant_type=urn:ietf:params:oauth:grant-type:device_code`. Respect interval/expiry and pending, cancellation, and error states. No app-operated relay is inherent to this flow. [Official requests and responses](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/#starting-the-dcf-flow-for-your-user).
3. Persist refresh-token rotation atomically: Twitch documents single-use refresh tokens and a 30-day inactivity expiry for this flow. Use returned access-token expiry. Validate at startup and hourly; clear disconnected sessions. [Device token rules](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/#device-code-grant-flow), [validation requirements](https://dev.twitch.tv/docs/authentication/validate-tokens/).
4. A useful initial scope is `user:read:follows` for followed channels/live streams. These are Helix API features, independent of whether playback authentication works. [Get Followed Streams](https://dev.twitch.tv/docs/api/reference/#get-followed-streams).

**What still needs a browser?** The phone browser completes ordinary device consent; no TV WebView is required for that flow. Separately, Streamlink documents website-derived authentication because third-party OAuth credentials were rejected for playback access. Therefore public DCF tokens must not be assumed to unlock authenticated playback. Website/session acquisition or another supported playback mechanism would need separate investigation. A phone login cannot automatically transfer its Twitch session cookies to the TV, and it does not satisfy the TV's integrity challenge. [Streamlink authentication history and current procedure](https://streamlink.github.io/cli/plugins/twitch.html#authentication).

## Repository findings

- **[streamlink/streamlink](https://github.com/streamlink/streamlink):** reusable Python extractor and stream reader, not a decoder or TV player. Its Twitch plugin is the relevant integration surface. Keep its version pinned and updateable because acquisition depends on Twitch's private GraphQL behavior. [Pinned Twitch source](https://github.com/streamlink/streamlink/blob/8.6.3/src/streamlink/plugins/twitch.py).
- **[Stremio/stremio-core](https://github.com/Stremio/stremio-core):** Rust shared application logic: domain types, addon transport, state/effects, authentication, library, and catalog models. **It is not Stremio's video decoder, Android player widget, or a replacement for Media3/LibVLC.** Its README's old `stremio-players` link returned 404 during research. Use core as an architectural reference, not evidence that a reusable Stremio Android player is available there. [Core README](https://github.com/Stremio/stremio-core/blob/master/README.md).
- **[crackededed/Xtra](https://github.com/crackededed/Xtra):** strongest Twitch-specific Android reference. It embeds Media3 ExoPlayer/HLS/session, rather than Python Streamlink. Its manifest includes `LEANBACK_LAUNCHER` and does not require touch, so it has explicit TV declarations; this alone does not establish TV UX quality. Login code separates Helix and GraphQL/web tokens and uses WebViews, including Twitch's Android-TV login page. This demonstrates implementation complexity, not an official playback-auth contract. Code is AGPL-3.0; inspect before reusing it. [Dependencies](https://github.com/crackededed/Xtra/blob/master/app/build.gradle.kts), [manifest](https://github.com/crackededed/Xtra/blob/master/app/src/main/AndroidManifest.xml), [login](https://github.com/crackededed/Xtra/blob/master/app/src/main/java/com/github/andreyasadchy/xtra/ui/login/LoginActivity.kt), [license](https://github.com/crackededed/Xtra/blob/master/LICENSE).
- **[yuliskov/SmartTube](https://github.com/yuliskov/SmartTube):** actual Android TV application, useful for remote interaction, playback controls, and device-specific behavior. Its build wires Leanback modules and a customized older ExoPlayer tree (`exoplayer-amzn-2.10.6`); it is not a clean current Media3 starter or Twitch authentication implementation. [Module wiring](https://github.com/yuliskov/SmartTube/blob/master/settings.gradle).
- **[jellyfin/jellyfin-androidtv](https://github.com/jellyfin/jellyfin-androidtv):** actual TV client with a current Media3 backend, useful for separating player lifecycle, capabilities, and UI. Its backend constructs ExoPlayer, renderers, data sources, and track selection. Jellyfin's server/account mechanisms do not solve Twitch extraction or authorization. [ExoPlayer backend](https://github.com/jellyfin/jellyfin-androidtv/blob/master/playback/media3/exoplayer/src/main/kotlin/ExoPlayerBackend.kt), [dependency catalog](https://github.com/jellyfin/jellyfin-androidtv/blob/master/gradle/libs.versions.toml).

## Required proof before committing to the architecture

- Build/install the pinned candidate on real arm64 Android TV 14+ and x86_64 emulator; import Streamlink, lxml, Crypto, and Trio inside the app; exercise TLS and stream enumeration. Inspect native libraries and test a 16 KB environment before claiming broad newer-Android support.
- Play live H.264/AAC, then test offline channels, stale access, reconnect, quality changes, cancellation/channel switching, ad gaps, and activity teardown. Prove which path retains Streamlink processing. Test integrity-required acquisition explicitly; one anonymous success is insufficient.
- Test the app's own public-client QR consent, denial/expiry, refresh rotation, and revocation. Treat successful Helix access and successful authenticated playback as separate acceptance criteria.
- Provide TV launcher/banner declarations, remote-only focus/navigation, and no touchscreen requirement. Validate on hardware rather than considering a launchable APK a finished TV experience. [Android TV requirements](https://developer.android.com/training/tv/get-started/create).
