# SlinkTV chat: native feasibility and offline TV prototype

Checked 2026-11-08. This is research and a disposable HTML interaction study. **No native app code was changed.** Native Stream Wall remains the main-app direction. No Twitch credentials were accessed, no Twitch chat connection was opened, and no messages were sent. Public 7TV metadata/CDN files and pinned upstream source were fetched.

## Recommendation

Build a **read-only native chat panel around the existing Media3 PlayerView**, initially using authenticated EventSub WebSocket with explicit `user:read:chat` consent. Keep sending out of this phase. Offer Docked, Over video, and Hidden; a player Show/Hide chat button and a dedicated shortcut restore the last visible mode. Animated WebP/GIF can use Android's image APIs; there is no demonstrated need for a WebView.

Anonymous IRC is technically plausible and implemented in both inspected clients, but it is a separate compatibility option with weaker documentation guarantees. It must not be presented as an official anonymous EventSub mode. Requiring chat consent is the cleanest supported default; a product decision could later add clearly labeled guest read-only IRC.

Existing code evidence: `app/src/main/java/tv/slink/app/TwitchApi.java:18` requests **only `user:read:follows`**. `PlayerActivity.java` builds a FrameLayout with a full-screen PlayerView plus bottom controls, disables Media3's built-in controls, intercepts D-pad/media keys, and releases the player in `onStop`. `app/build.gradle` has minSdk 34 and Media3 1.9.3. The login's working follows permission does not establish chat permission or authenticated playback. See [phase2-research.md](phase2-research.md) and [ui-ux-research.md](ui-ux-research.md).

## Twitch transport and permissions

| Route | Read authorization | Send authorization | Fit for this app |
| --- | --- | --- | --- |
| EventSub WebSocket + Helix | User access token with `user:read:chat`; subscription `user_id` is that token's user, `broadcaster_user_id` is the watched channel. | Separate `user:write:chat`; POST `/helix/chat/messages`, not WebSocket traffic. | Recommended installed-client route; no server/secret required. |
| Authenticated IRC | User token with `chat:read`; PASS `oauth:<token>` and matching lowercase NICK. | Separate `chat:edit`, IRC PRIVMSG. | Legacy alternative; these scopes differ from EventSub scopes. |
| Anonymous IRC | Existing clients use NICK `justinfan` plus digits without a real user token. | Cannot send as a user. | Compatibility option; not a current documented OAuth guarantee, not tested live here. |
| App-token/cloud EventSub | Extra user/broadcaster authorizations (`user:bot`, and broadcaster `channel:bot` or moderator status) apply. | Additional send grants apply. | Unnecessary for one TV viewing as its signed-in user; do not introduce a client secret. |

Sources: [Twitch chat authentication](https://dev.twitch.tv/docs/chat/authenticating/), [Channel Chat Message authorization](https://dev.twitch.tv/docs/eventsub/eventsub-subscription-types/#channelchatmessage), [IRC concepts](https://dev.twitch.tv/docs/chat/irc/), [Send Chat Message](https://dev.twitch.tv/docs/api/reference/#send-chat-message). Current IRC documentation describes authenticated access; anonymous evidence below is deliberately distinguished from that contract.

### Consent and token lifetime

Suggested requested set for a future read-only upgrade: `user:read:follows user:read:chat`. Start a new Public-client device authorization and validate the resulting granted scopes. Refresh does not acquire missing consent. Handle refusal as a usable video player with chat unavailable, not a failed login for the whole app. Do not request write/moderator/bot scopes merely to display chat.

Public DCF requires no secret. Twitch describes four-hour access tokens; honor returned `expires_in`. Public refresh tokens rotate and are single-use. The DCF page says 30-day inactivity expiry, whereas the refresh page says Public refresh tokens expire 30 days after generation; do not promise indefinite login. Refresh with `client_id`, `grant_type=refresh_token`, encoded `refresh_token`, no secret, serialize callers, and persist the replacement pair atomically. Reauthorization is needed after terminal refresh failure. [Device flow](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/#device-code-grant-flow), [refresh rules](https://dev.twitch.tv/docs/authentication/refresh-tokens/).

Validate at startup and hourly, including during a long viewing session. Confirm client ID, user ID, and chat scope; end revoked sessions. Reuse the existing session owner rather than adding independent token refresh inside chat. API 401 can indicate expiry, wrong user/client, or missing scope; avoid retry loops. [Validation contract](https://dev.twitch.tv/docs/authentication/validate-tokens/).

### EventSub lifecycle

Connect to `wss://eventsub.wss.twitch.tv/ws`; on welcome, create Helix EventSub subscriptions using its session ID and a user bearer token. Default initial subscription deadline is ten seconds. EventSub is receive-only except WebSocket pong; subscription requests are HTTPS, not messages on this socket. Reset a watchdog on notifications/keepalives using the returned timeout. On server reconnect, use its URL unchanged, retain the old connection until the new welcome, and complete the handoff within 30 seconds; subscriptions transfer. On an ordinary lost connection, reconnect and recreate subscriptions: missed events are not replayed. Handle authorization revocation. Limits are three enabled connections per user-token/client-ID tuple, 300 enabled subscriptions per connection, and total cost ten. [WebSocket lifecycle and limits](https://dev.twitch.tv/docs/eventsub/handling-websocket-events/), [creating subscriptions](https://dev.twitch.tv/docs/eventsub/manage-subscriptions/).

Proposed client behavior: one connection for the currently viewed channel, bounded deduplication by EventSub envelope ID and chat message ID, and channel/session generation IDs on all callbacks. Exponential reconnect backoff with jitter should stop on revoked consent. A visible “Reconnecting; some messages may be missing” line is more honest than claiming complete history. Do not invent backlog from a later connection. Channel switches must cancel obsolete subscription work and remove old subscriptions.

### Moderation and message shape

Subscribe to four version-1 events for the same broadcaster/reader: `channel.chat.message`, `channel.chat.message_delete`, `channel.chat.clear_user_messages`, `channel.chat.clear`. All use the reader's `user:read:chat` with a user token. No moderator grant is necessary merely to observe these deletions. Delete by message ID, clear a user's messages by `target_user_id`, and clear the full window for a room clear. Preserve broadcaster/source IDs for Shared Chat; names alone are not identities. EventSub messages supply structured fragments, message IDs, chatter identity, color, badges, and source fields. [Subscription contracts and examples](https://dev.twitch.tv/docs/eventsub/eventsub-subscription-types/).

Proposed reducer: apply moderation immediately to both visible rows and pending render batches; keep a small expiring deleted-ID set so a delayed duplicate cannot resurrect a removed message. On a disconnect, discard the old window rather than showing potentially deleted messages indefinitely. Render chat text as plain text/spans, not HTML. Use Twitch emote fragments first, then match 7TV names only in ordinary text fragments. Unknown fragments fall back to their text. Badge fetch failure must not hide the message. Handle empty/illegible nickname colors with a readable fallback, retaining the original color as metadata.

IRC needs `twitch.tv/tags` and `twitch.tv/commands` for useful metadata, CLEARMSG and CLEARCHAT; membership floods are unnecessary. Parse CRLF framing, escaped IRC tags, Unicode emote offsets, PING/PONG, RECONNECT, NOTICE failures, and per-message IDs. CLEARMSG targets one message; CLEARCHAT can target one user's messages or the entire room. [IRC protocol and tags](https://dev.twitch.tv/docs/chat/irc/), [IRC migration mapping](https://dev.twitch.tv/docs/chat/irc-migration/).

### Limits and sending boundary

Normal users have a 100-room concurrent join limit; 20 joins per ten seconds, and 20 IRC authentication attempts per ten seconds. These are account-wide concerns, not per-TV allowances. Sending has separate limits: ordinarily 20 messages/30 seconds and one per second per channel; broadcaster/moderator/VIP allowances differ. Helix Send Chat Message has a separate rate bucket; honor rate-limit headers and 429s. [Chat limits](https://dev.twitch.tv/docs/chat/#rate-limits).

If sending is ever requested, add explicit write consent and a deliberate send action. Helix `sender_id` must match the user token; messages are limited to 500 characters. Inspect `is_sent` and `drop_reason`, not HTTP success alone. User-token sends in Shared Chat fan out to the shared session; `for_source_only` is an app-token-only setting. Room restrictions/AutoMod remain separate from possession of a scope. This prototype has no composer or send path. [Send Chat Message](https://dev.twitch.tv/docs/api/reference/#send-chat-message).

## 7TV: current data and updates

The current monorepo was inspected at **`5606ada34724324875f6961eebad51e1e3d9044b`**. Do not rely exclusively on the archived API/EventAPI repos. The public global endpoint was fetched without authentication on the research date; selected WebP CDN files were downloaded and decoded locally. No live EventAPI session was exercised.

| Request | Use |
| --- | --- |
| `GET https://7tv.io/v3/emote-sets/global` | Global enabled set; use the returned set ID, not a hardcoded legacy ID. |
| `GET https://7tv.io/v3/users/twitch/{broadcasterId}` | Twitch ID lookup, active `emote_set` / `emote_set_id`, and 7TV user identity. |
| `GET https://7tv.io/v3/emote-sets/{setId}` | Reload a particular set after change or reconnect. |
| `wss://events.7tv.io/v3` | Update notifications; separate from Twitch's connection. |

Current source: [REST emote sets](https://github.com/SevenTV/SevenTV/blob/5606ada34724324875f6961eebad51e1e3d9044b/apps/api/src/http/v3/rest/emote_sets.rs), [platform user lookup](https://github.com/SevenTV/SevenTV/blob/5606ada34724324875f6961eebad51e1e3d9044b/apps/api/src/http/v3/rest/users.rs#L518). Missing account/set is a valid empty channel-emote result; failures should retain cached metadata with a stale state. IDs are opaque strings: the observed global response uses ULID-shaped IDs, not exclusively 24-character historical IDs.

An enabled set entry's `name` is its channel alias; `data.name` is the original emote name. Index the alias case-sensitively and retain the original name/owner for attribution. Width/height come from the selected `data.host.files` variant; normalize protocol-relative `host.url` to HTTPS and append the returned file name. Do not assume square images or fixed `/4x.webp` availability. `data.flags & 256` is global/default zero width; the enabled entry's `flags & 1` is a separate per-set zero-width flag. Both need handling; testing only equality with 256 misses combined flags. [Enabled entries and flags](https://github.com/SevenTV/SevenTV/blob/5606ada34724324875f6961eebad51e1e3d9044b/shared/src/old_types/mod.rs#L623), [image variants](https://github.com/SevenTV/SevenTV/blob/5606ada34724324875f6961eebad51e1e3d9044b/shared/src/old_types/image.rs).

Proposed resolution: Twitch's structured emote identity wins by default; channel 7TV aliases then global 7TV aliases fill text-token matches. Explicit provider override flags should be a separately tested choice. Multiple aliases can share one image cache entry. A rename changes lookup keys, not the asset identity. A removed emote should stop matching new messages; decide explicitly whether old immutable message tokens retain their already resolved image. Deletion/moderation must always override rendering caches.

### EventAPI trap: resume is not implemented in current source

V3 uses hello (op 1), heartbeat (2), dispatch (0), reconnect (4), ACK (5), error (6), end-of-stream (7), subscribe (35), and unsubscribe (36). Subscribe to `emote_set.update` with `condition.object_id` equal to each active global/channel set ID. Hello advertises heartbeat interval and subscription limit. Do not treat WebSocket protocol ping as the application heartbeat. [Archived protocol documentation](https://github.com/SevenTV/EventAPI#api-documentation).

The archived documentation describes resume/replay, but **current server source explicitly responds to Resume with `success:false`, `dispatches_replayed:0`, `subscriptions_restored:0`**. Reconnect must resubscribe and re-fetch snapshots; do not promise gap-free emote updates. The current server has a connection TTL and heartbeat schedule, so reconnect is normal. [Exact current implementation](https://github.com/SevenTV/SevenTV/blob/5606ada34724324875f6961eebad51e1e3d9044b/apps/event-api/src/http/v3/mod.rs#L623).

Proposed implementation: use events to invalidate and debounce a full set reload first. This handles `pushed`, `pulled`, `updated`, nested/partial rename payloads, and multiple changes without building a brittle patch parser. Subscribe before reloading and mark the snapshot dirty if changes arrive while fetching. Re-fetch the broadcaster's active-set mapping on reconnect and periodically (e.g. five minutes while visible); a subscription to the old set alone cannot discover a set switch. A tested `user.update` subscription can optimize this later. Respect server errors/limits, back off with jitter, avoid duplicate subscriptions, cancel old-channel requests, and keep one 7TV connection. These are suggested policies, not a guaranteed public SLA or measured service limit.

## Native emotes and Media3

Android API 28+ `AnimatedImageDrawable` / `ImageDecoder.decodeDrawable` support animated GIF and WebP; minSdk 34 satisfies that baseline. Decode off the UI thread, select a suitably sized variant, set target dimensions, and start/stop animation with visibility. `ImageDecoder` provides target sizing and decode callbacks. [AnimatedImageDrawable](https://developer.android.com/reference/android/graphics/drawable/AnimatedImageDrawable), [ImageDecoder](https://developer.android.com/reference/android/graphics/ImageDecoder).

Android documents baseline AVIF image decoding, but that table is **not proof of animated AVIF playback in AnimatedImageDrawable**. AV1 video decoding in Media3 also does not prove animated AVIF emote support. Use WebP first, GIF fallback, static variant/text fallback; only enable AVIF animation after a real target-device decoder/frame test. The inspected Frosty implementation explicitly excludes AVIF for its Flutter renderer; that is not a statement about all Android decoders. [Android format table](https://developer.android.com/media/platform/supported-formats), [Frosty selection](https://github.com/tommyxchow/frosty/blob/3ea6ccd43508fd162b045c7b0a4760716d6bcfd1/lib/models/emotes.dart#L225).

Media3 PlayerView supports aspect-ratio resize modes and ordinary view overlays. A sibling native chat panel in the current FrameLayout can render over the video without changing playback media or adding a second decoder. Keep the video surface's normal composition order; do not set it on top of application overlays. Use `RESIZE_MODE_FIT` when docking, update bounds without recreating ExoPlayer, and test SurfaceView resize/overlay behavior on the actual TV. A view overlay is distinct from Media3 Transformer export effects. [PlayerView API](https://developer.android.com/reference/androidx/media3/ui/PlayerView).

Suggested layout/rendering design:

1. A `ChatPresentation` state owns mode (Hidden/Docked/Overlay), last visible mode, width, background opacity, and text scale. Docked reserves roughly 28% of screen width and fits video into the rest. Overlay keeps full video bounds and uses a translucent panel background; do not set alpha on the entire chat View because that fades text/emotes too.
2. A lifecycle-owned `ChatSession` produces immutable message/deletion/connection events for one broadcaster and account generation. A reducer owns bounded messages and deduplication. `PlayerActivity` only binds it and routes controls; playback must continue if chat fails.
3. Use RecyclerView plus a text/spans renderer. A custom `ReplacementSpan` measures an emote run at the font's chosen emote height, preserving `width/height`. Allocate line metrics for image height and place it consistently against the baseline. Wrap a base emote plus following zero-width layers into **one measured run**; draw layers in order over the base, centered/aligned consistently, without extra advance. A leading zero-width token needs a defined standalone/text fallback. Cap layer count and width; never squash a wide image to a square.
4. Animated drawables in spans need explicit invalidation ownership: install callbacks that invalidate the owning text row, detach them on recycle, stop animations off screen/hidden/background, and discard stale asynchronous loads by row/message ID. Do not share one mutable Drawable callback among multiple views. Share encoded bytes/cache entries, or deliberately build a synchronized renderer with reference-counted visible consumers.
5. Show/Hide is one player button. Proposed native shortcut: `KEYCODE_PROG_YELLOW`, with configurable alternative on remotes without color keys; HTML uses C and the browser Yellow key value. Handle first ACTION_DOWN only, consume key-up/repeats appropriately, and check chat shortcut before generic D-pad handling. Preserve play/pause keys. Back closes chat options, then player controls, then returns to the channel; don't require hiding chat first. The current Back handler always finishes, so this would need an explicit update later.

### Resource budget proposal, not a benchmark

Start with 100 retained native messages, 200 pending events, at most 20 incoming render batches/second, 12 simultaneous visible animated emote instances, four layers per composite, two image decodes and four downloads in flight. Prioritize moderation over ordinary-message overload; drop oldest unrendered normal messages with a visible catch-up indicator. Text must remain usable when image budgets are exhausted. The prototype uses a smaller **24-message** cap to make eviction easy to inspect.

Provisional image budgets: 16 MiB decoded-image working budget, 64 MiB encoded disk LRU, 2 MiB maximum download per selected variant, 512×512 maximum decoded dimensions (and a pixel-count cap), and 200-frame metadata threshold before static fallback. These are starting safeguards, not safe universal limits. AnimatedImageDrawable internals are not fully accounted by a bitmap LRU; measure process/native/GPU memory and dropped frames with video playing. A 128×128 RGBA frame alone is 64 KiB; eagerly expanding 100 frames would be 6.25 MiB **per emote** before overhead. Prefer the smallest variant meeting physical display pixels, not 4x by default. Bound JSON/message sizes too; verify actual bytes/dimensions rather than trusting CDN metadata.

Use conditional HTTP cache behavior where supported, bounded metadata refresh, and negative caching for missing sets. Stop expensive image updates immediately when hidden; either retain a small session buffer briefly or disconnect after a grace period. On return from a disconnected state, start a fresh window and mark the gap. Do not persist transcripts as part of the emote disk cache. Channel/account switch must not reuse the wrong set mapping.

## Delivered prototype and verification

- [chat-ui-prototype.html](prototypes/chat-ui-prototype.html): complete offline HTML, **212,093 characters / 212,123 UTF-8 bytes**, below the 490,000-character limit. All five emotes and the game frame are data URLs; no login or live API/network dependency. Final copy uses functional labels; revealing controls focuses Pause.
- [chat-ui.template.html](prototypes/chat-ui.template.html) and [chat-build.py](prototypes/chat-build.py): editable source and isolated builder. Rebuild with `rtk proxy python docs/prototypes/chat-build.py` (Pillow required). Shared `build.py` was untouched.
- [chat-preview-checks.js](prototypes/chat-preview-checks.js): checks injected only into a temporary preview; not shipped in final HTML. Covers 18 assertions: dock/overlay 16:9 geometry, arrow focus, options, independent background opacity, Escape focus restoration, shortcut hide/restore, 24-message eviction, deletion, clear, composite structure, embedded images, hidden-control focus and OK reopening.
- Animated files were independently decoded with Pillow: Clap 2 frames, PETPET 5, PartyParrot 10; peepoHappy/7Cinema static. 7Cinema is 170×64, visibly wide. Actual native animation performance remains untested.

Initial preview results at width 1440: `contentHeight:1077`, `capturedHeight:1077`, `consoleMessages:[]`. After the final copy/layout pass, root previewed at width 728: `contentHeight:669`, `capturedHeight:669`, `consoleMessages:[]`. The final assertion preview logged `PASS 18 chat prototype assertions` with no errors. Docked and overlay screenshots were inspected. Synthetic key tests cover application handlers; native remote hardware and browser trusted Enter defaults were not automated. Mouse handlers and DOM state transitions were exercised via clicks.

One initial preview received a shell error instead of HTML because Windows Python stdout used cp1252: `UnicodeEncodeError: 'charmap' codec can't encode character '\\u2161' in position 155738: character maps to <undefined>`. That preview had `contentHeight:58`, `consoleMessages:[]`. Reading with `rtk proxy python -X utf8 ...` fixed the transport; it was not an HTML runtime error. Use UTF-8 when passing the file to the rendering tool.

Native implementation order: (1) fixture-driven presentation/remote controls on the existing player, (2) explicit chat scope upgrade and one EventSub lifecycle with moderation, (3) plain-text bounded chat and connection states, (4) global/channel 7TV metadata plus static images, (5) animated/zero-width rendering and resource budgets, (6) live consent/reconnect tests with SlinkTV's own Public client and TV playback soak tests. Verify rotation/background/channel changes, Shared Chat source IDs, Unicode, repeated deletion, set rename/replacement, missing assets, high-rate bursts, low memory, and video frame stability before considering native chat complete.
