# Twitch-box UI, features, and follow-refresh research

Research date: 2026-11-08. Upstream checkout `.tools/research/twitch-box` was verified with `git rev-parse HEAD` as **23bcb074a546c1c891d652d21ac4f6e0960894c0**. All upstream code links below are pinned to that commit. SlinkTV references describe the current working tree and its documented **0.3.0** behavior, not a committed release snapshot.

This is a source inspection. No upstream build, script, app, or live authenticated workflow was run. Existing SlinkTV verification results are reported in [phase3-verification.md](phase3-verification.md), not independently reproduced here. Playback resolution, proxies, signed URLs, VOD playback, and live-cache internals are outside this report's scope.

## Findings

**The quoted “event-driven refreshes” feature is an in-process follow-change invalidation mechanism.** It is feasible in SlinkTV without a server, EventSub, or a Kotlin rewrite. It avoids refreshing a list merely because the user visits it again. It does **not** automatically discover follows made on another device, streams going live/offline, or newly published videos. Those need a separate reconciliation/freshness policy.

Twitch-box has a much broader browsing and saved-content UI, local channel/category follows, native chat including animated third-party emotes, and an optional mini-player. SlinkTV currently offers a smaller three-column live Stream Wall with explicit Refresh, straightforward remote controls, and optional device-local viewing relevance. Feature breadth is source-proven; comparative smoothness, reliability, visual polish, and TV performance are runtime untested.

### Chat and animated 7TV

Twitch-box contains native chat implementation, not just UI screenshots. Its default read path uses IRC over WebSocket; a raw IRC socket is another branch. EventSub chat is gated by `DEBUG_EVENT_SUB_CHAT`, default false, and a Helix token. Its subscription list is `channel.chat.clear`, `channel.chat.message`, `channel.chat.notification`, and `channel.chat_settings.update`. [Transport selection][tb-chat], [EventSub subscriptions][tb-chat-events].

The emote loaders include Twitch plus **7TV, BetterTTV, and FrankerFaceZ**; third-party providers are preference-controlled. 7TV parsing chooses WebP or GIF/PNG assets, preserves animation metadata and an overlay-emote flag. Visible chat rows start `Animatable` drawables, including layered images, and stop them when detached. There is also a 7TV Event API handler for emote-set updates. This substantiates animated/overlay support in source, without promising every format, every zero-width case, or low-end TV performance. [Loaders][tb-chat-providers], [7TV parsing][tb-7tv-parse], [animation lifecycle][tb-animated], [7TV updates][tb-7tv-events].

SlinkTV's chat research and HTML demonstration are **not native chat shipped in 0.3.0**. The native player currently constructs playback controls only. [PlayerActivity.java:147](../app/src/main/java/tv/slink/app/PlayerActivity.java#L147), [verification and chat boundary](phase3-verification.md). Animated 7TV capability in Twitch-box is therefore a real implementation gap, not evidence that SlinkTV's proposed chat design cannot work.

## Exact follow-refresh mechanism

### Events and affected lists

| Successful action in Twitch-box | Version change | Dependent list |
| --- | --- | --- |
| Save/delete a local channel follow after the DAO operation | `channels += 1` | Live and Channels |
| Account channel follow/unfollow accepted by GraphQL, with no reported mutation error | `channels += 1`, `accountChannels += 1` | Live, Channels, and account-followed Videos |
| Save/delete a local game follow | Games counter `+= 1` | Games |
| Account game follow/unfollow accepted by GraphQL | Same Games counter `+= 1` | Games |
| Update cached local name/logo/box art | No version notification in `update()` | None through this mechanism |

The channel repository exposes `MutableStateFlow(FollowChangeVersions(0, 0))`; the game repository exposes `MutableStateFlow(0L)`. These are versioned current-state signals, not a durable event log. The channel page and both player ViewModels notify on successful account mutations; local save/delete methods notify themselves. Failed/integrity-rejected account mutations do not reach the success notification. [Channel repository][tb-local-ch], [game repository][tb-local-game], [channel mutations][tb-channel-mutations], [game follow][tb-game-add], [game unfollow][tb-game-remove], [Media3 player][tb-player-follow], [other player][tb-player-follow-legacy].

### Lifetimes and version consumption

| State | Owner/lifetime | Consequence |
| --- | --- | --- |
| Local follows | Room entities, accessed through app-owned repositories | Membership survives process death; local data is device-scoped. |
| Change counters | Lazily created repositories in the application's `XtraModule` | Shared across screens during that app process; initialized to zero after process restart, not persisted. |
| List pages | `Pager` flows cached in each list ViewModel's scope | View recreation can reuse already loaded pages; these are not durable disk snapshots. |
| Live's consumed version | `FollowedStreamsViewModel.consumedFollowVersion` | Collector runs in `viewModelScope`, compares channel version, updates consumed version, and invalidates the current paging source. It can invalidate while its view is absent. |
| Games/Channels/Videos consumed version | Fragment field reset to current repository value in `onViewCreated`; collector runs while view is STARTED | A change while the same view is stopped is observable on restart. Recreating the view resets its comparison baseline. |

Sources: [app/module ownership][tb-app], [repository construction][tb-module], [Live implementation][tb-live-vm], [Games fragment][tb-games-fragment], [Channels fragment][tb-channels-fragment], [Videos fragment][tb-videos-fragment], and cached flows for [Games][tb-games-vm], [Channels][tb-channels-vm], [Videos][tb-videos-vm].

**Source-derived lifecycle limitation, not runtime reproduced:** if Games, Channels, or Videos retains an old ViewModel/page cache, its view is destroyed, and a relevant mutation happens before view recreation, `onViewCreated` seeds the latest counter as though consumed. The first replay then compares equal and does not refresh that retained cache. Live explicitly avoids this particular gap by keeping consumption beside its paging source. Do not generalize the README's Live guarantee to all four tabs.

Live advances its counter before invalidation/load completion; the counter means “change observed,” not “fresh data successfully loaded.” Its nullable source permits a no-op before a source exists; the first source subsequently loads current membership. Errors still need retry handling. StateFlow can coalesce rapid changes; a differing latest version is enough to invalidate, so an event-per-click delivery guarantee is unnecessary. Android documents current-state replay and lifecycle collection separately from persistence. [Live code][tb-live-vm], [Android StateFlow guidance](https://developer.android.com/kotlin/flow/stateflow-and-sharedflow).

### What does not trigger it

No external-follow or stream-status EventSub receiver feeds these counters in the inspected source. A phone/web follow change, an already-followed streamer starting/stopping, viewer-count changes, or a new video publication does not itself increment them. Returning to a retained list with unchanged versions is therefore not proof of current network data.

Other reload paths still exist: new Pager/load, changed filters, swipe refresh, and integrity-token refresh; network restoration retries failed loads. The common adapter explicitly wires swipe refresh, but that alone does not prove an equally convenient remote-only Refresh action. [Common loading/refresh][tb-paged], [Games retry/integrity handlers](https://github.com/w1lli4m666-droid/Twitch-box/blob/23bcb074a546c1c891d652d21ac4f6e0960894c0/app/src/main/java/com/github/andreyasadchy/xtra/ui/following/games/FollowedGamesFragment.kt#L88-L97).

Twitch-box separately schedules an optional 15-minute WorkManager live-notification worker. It queries streams and posts Android notifications; it does not wire those results into these follow versions. Its existence must not be presented as real-time followed-list synchronization. [Scheduling][tb-notifications], [worker][tb-notification-worker]. Chat EventSub and 7TV events described above are likewise separate systems.

## What SlinkTV already refreshes

The current Java code is already observable, but not a versioned follow-mutation system:

- `SlinkApplication` shares one `AuthViewModel` account controller across activities. It owns a serial worker, in-memory snapshot, and `LiveData<State>`. Sessions are persisted separately. [Owner](../app/src/main/java/tv/slink/app/SlinkApplication.java#L7), [state/worker](../app/src/main/java/tv/slink/app/AuthViewModel.java#L24).
- Session restore, successful login, manual `refreshData()`, and scheduled validation call `loadData()`, which fetches profile plus **all pages of followed channels and followed live streams**, publishes Ready, then schedules again. [AuthViewModel.java:117](../app/src/main/java/tv/slink/app/AuthViewModel.java#L117), [loadData:167](../app/src/main/java/tv/slink/app/AuthViewModel.java#L167), [TwitchApi.java:104](../app/src/main/java/tv/slink/app/TwitchApi.java#L104).
- The validation timer runs only while foregrounded; its delay is the earlier of the next hourly validation or token-expiry margin, with a minimum delay. Its callback currently reloads account data too. Foreground return reschedules that deadline; it does not always fetch immediately. Thus “SlinkTV only updates on manual Refresh” would be inaccurate. [AuthViewModel.java:199](../app/src/main/java/tv/slink/app/AuthViewModel.java#L199).
- MainActivity reloads when it receives a different snapshot object or signs in. Its Following load builds cards from that snapshot's `live()` array. Switching back to Following can rebuild cards from the same old live snapshot rather than discover newly live channels. Player return normally re-sorts/restores focus without fetching new follows. [Account observer](../app/src/main/java/tv/slink/app/MainActivity.java#L103), [load](../app/src/main/java/tv/slink/app/MainActivity.java#L204), [resume](../app/src/main/java/tv/slink/app/MainActivity.java#L412).
- `generation` fields discard obsolete async results. They are request/session cancellation guards, not membership revisions or proof of cache freshness. [Account request](../app/src/main/java/tv/slink/app/AuthViewModel.java#L54), [wall result guard](../app/src/main/java/tv/slink/app/MainActivity.java#L239).

## Feasibility and proposed SlinkTV approach

**Yes for local change invalidation; qualified yes for all four content families.** The four upstream tabs require data/UI features SlinkTV does not yet have. Adding counters alone does not add local follows, category lists, or video browsing.

### API boundaries established by official sources

- Official Get Followed Channels and Get Followed Streams use `user:read:follows`, which SlinkTV already requests. Get Streams can resolve a stored set of channel IDs/logins with an app/user token. Get Videos supplies published metadata by broadcaster; an account-followed video feed would require client aggregation. The current reference exposes no followed-games endpoint. [Twitch API reference](https://dev.twitch.tv/docs/api/reference/).
- Official follow/unfollow write endpoints were removed. Twitch-box's GraphQL mutation implementation is not a supported Helix capability to add under SlinkTV's existing token. Local favorites are straightforward; Twitch-account mutation parity is a separate unofficial-integration decision. [Twitch's removal announcement](https://discuss.dev.twitch.com/t/deprecation-of-create-and-delete-follows-api-endpoints/32351).
- `channel.follow` v2 describes a broadcaster receiving a follower and requires `moderator:read:followers`. Its condition requires the relevant broadcaster/moderator identity. It is not a viewer-wide “my follows changed” feed, and the subscription catalog has no equivalent viewer unfollow feed. [Subscription type](https://dev.twitch.tv/docs/eventsub/eventsub-subscription-types/#channel-follow), [condition](https://dev.twitch.tv/docs/eventsub/eventsub-reference/#channel-follow-condition).
- `stream.online`/`stream.offline` can signal a specified broadcaster's transitions without event-specific scopes. WebSocket subscriptions still require a user access token, so this is not anonymous EventSub. [Stream event types](https://dev.twitch.tv/docs/eventsub/eventsub-subscription-types/#stream-online), [WebSocket authentication](https://dev.twitch.tv/docs/eventsub/handling-websocket-events/#authentication).
- WebSocket limits are currently three connections, 300 enabled subscriptions per connection, and total cost 10 per client/user tuple. Unauthorized-by-the-broadcaster stream subscriptions incur cost; following a channel is not that broadcaster authorizing your app. Broadcaster consent changes cost rules. Do not promise unlimited push coverage of a viewer's follow list. [Limits/cost model](https://dev.twitch.tv/docs/eventsub/manage-subscriptions/#subscription-limits).
- A lost WebSocket requires resubscription; missed events are not replayed. Push therefore still needs snapshot reconciliation. [Twitch WebSocket lifecycle](https://dev.twitch.tv/docs/eventsub/handling-websocket-events/).

### Proposed design, not implemented

1. **Keep durable membership separate from refresh state.** If local favorites are added, persist them first, then publish a typed change/revision. Decide explicitly whether local favorites are device-wide (Twitch-box behavior) or account-scoped. Keep signed-in snapshots keyed by account; discard obsolete account results at logout/switch.
2. **Own revisions beside the retained data.** A Java repository/controller can expose LiveData containing membership revisions and list state. Retain the last successfully loaded revision and a dirty/pending state outside the Activity view. Preserve dirty state across view recreation and retry failures. On process restart, reconstruct local membership and load remote snapshots; no durable event journal is necessary unless durable cached pages are also introduced. Android's lifecycle-aware LiveData supports the Java UI already in use. [Official LiveData guidance](https://developer.android.com/topic/libraries/architecture/livedata). Paging is optional, not a prerequisite; if adopted, its source/retained-flow model is documented by [Android Paging](https://developer.android.com/topic/libraries/architecture/paging/v3-paged-data).
3. **Invalidate only actual dependencies.** Local channel changes affect local Channels/Live; account membership changes affect account Channels/Live and any future aggregated Videos; game changes affect Games. Sort/language changes use their own list/query key. Do not reload unrelated lists or restart playback because a favorite changed.
4. **Reconcile remote state separately.** Preserve a visible Refresh action. Add a deliberate staleness policy on foreground/navigation and optional refresh while the wall is visible; coalesce requests through the existing serial account owner. Compare complete account membership snapshots to detect external follow/unfollow changes. Track live/video freshness independently of membership: no follow change is required for a stream to start or a video to appear. Exact intervals are product choices to validate, not claims about upstream.
5. **Keep token validation independent of browse freshness.** Preserve SlinkTV's account validation/rotation guarantees when splitting data refreshes. Avoid making every catalog event call today's full `refreshData()`: it increments the auth generation, validates, and fetches all account lists. Continue rejecting results from obsolete sessions/queries.
6. **Preserve TV focus and errors during refresh.** Retain cards during background reload, update by channel identity, and choose a nearby surviving card if the focused item disappears. Publish an error without treating failed remote retrieval as an empty followed list. Avoid refreshes that repeatedly steal focus or reorder a card while the user is selecting it.
7. **Treat push as optional augmentation.** If later needed, use bounded online/offline subscriptions with reconnect/deduplication/resync handling and actual subscription-cost checks. Local events plus controlled reconciliation are sufficient for the upstream feature claim; full-list EventSub coverage is not a prerequisite and may not fit its cost budget.

For an initial SlinkTV increment, the useful work is a retained Following state with explicit freshness and reliable refresh/focus behavior. If local favorites are desired, add durable channel membership and emit local mutations into that state. Games and account-followed Videos are independent feature increments; their existence should not be implied by the refresh infrastructure.

### Checks required before claiming runtime parity

These are proposed acceptance cases, not tests run in this research:

- Local follow/unfollow updates only dependent lists, including changes made inside the player.
- Mutation while a list is visible, stopped, view-destroyed, and Activity-recreated; reopening without any change causes no unnecessary fetch.
- Failed mutation causes no success event; failed reload remains retryable; repeated changes coalesce without losing the final membership.
- Process restart restores local favorites; logout/account changes cannot display the old account's results.
- An external phone follow/unfollow and a stream online/offline transition are found by reconciliation even when local revision is unchanged.
- Focus survives insertion/removal/reorder; refresh errors retain cards; the remote can invoke Refresh.
- Chat providers, animated 7TV, downloads, and mini-player require separate device acceptance if implemented; source availability alone is not runtime validation.
